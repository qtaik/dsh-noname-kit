# 无名杀扩展开发规范

你在为开源三国杀游戏 Noname 编写扩展。本文件是开发流程与专业规范的主来源；Agent 定义目标与判断原则，工坊任务消息提供本次需求，工具说明和程序决定可用参数及写入限制。

## 资料与实现原则
目标是完成用户已授权的武将、卡牌或模式，规范用于减少错误。需求确认是避免误解的交互流程，不是工具执行前的程序审批。路径检查、备份、语法校验和防止误删等保护以工具实际结果为准，不用提示词承诺替代程序保障。
用户提供教程目录后，可用通用只读工具按需查看目录和相关章节；教程用于理解与定位，API 疑问和版本差异以当前游戏源码为准。参考搜索/内容目录工具没有自动索引外部 Markdown 教程。资料足够时继续制作，不要求读完整套教程或穷举所有参考。

需要章节地图、触发/选择/标记/卡牌/模式/联机的制作检查时，按需阅读[制作与排错指南](references/development-guide.md)。相对路径以 skill_load 返回的技能资源目录为基准；无法定位时利用已有资料和当前源码继续，不全盘搜索。

## 任务粒度(重要)
**一个任务 = 一个完整武将(含全部技能)、一张卡牌,或一个完整的自定义游戏模式(mode 类型,见下节)。**首次实现武将任务时,理解与实现覆盖全部技能;按实际文件完成写入后收口，不把多文件写入称为一次原子提交。后续反馈只修复对应技能,其他技能的确认状态保持不变。

## 🎲 自定义模式(玩法)任务(mode 类型)
交付物是一个能从主菜单进入、完成选将开局、执行规则并正常结算的独立模式。按当前引擎与相近模式核对注册入口和必需字段；教程或旧项目里的版本标签不作为当前 API 保证。

- 确认核心玩法、人数与阵营、先手、逐条规则及胜负时机；一条规则对应一个任务节点，完成后由 noname_skills_written 登记实际实现的节点。
- 根据当前源码选择注册时机、设置读取、选将、玩家 ID、座次、牌堆、AI 态度和回合循环。game.addMode 等名称只作定位线索，使用前核对本机定义与相近模式的实际调用。
- 明确事件编译方式：步进函数、async content 与模块闭包的可用范围分别核对；临时技能的有效期、距离修正、摸牌事件及换座处理依本次机制实现，不套用某个旧模式的固定写法。
- 界面优先复用引擎对话框和节点；玩法确需定制时处理缩放、关闭、清理和联机交互，并在用户实际 UI 环境中验证。
- 先完成最小闭环，再核对正常结束、失败/取消和再次开局。未实测的入口、联机或 UI 兼容性明确列为未验证，不把静态检查当作游戏运行成绩。


## 开发流程
1. **理解需求与授权**：只读讨论按用户要求答复。用户已明确要求制作或修复且需求完整时，简述本次目标与关键规则后执行；工坊提交的表单是对应需求的执行请求，不需机械等待额外一句「确认」。有玩法歧义、缺少关键数值或交互决定时先提问；方案尚未选定或用户只要求讨论时，不进入修改。澄清回答已确定方案且制作授权仍有效时继续执行。同一方案的续做和反馈修复不重复确认；出现新的玩法取舍或明显扩大范围时再请用户决定。按任务关注触发、频率、目标、数值和边界，无需对简单改动重复完整确认模板。
2. **ID 前缀约定**:任务带「内部 ID 前缀」时,新增内部 ID = 前缀 + 拼音/英文(如 cs_tianfa),显示名写入 translate。
3. **找官方参考**:用 `noname_search_reference` 直接搜官方相似实现(中文名/ID/效果关键词;整句描述按相似度列候选)。按本次所需机制寻找参考，可组合已实际读到的不同实现，不要求找到完全相同的机制组合。已有足够参考支持当前方案时停止扩查，无需穷举候选或等 coverage 完整；未搜完仍不能声称内容不存在。参考仍不足时，仅针对缺少依据的机制调整关键词或定位源码。澄清期间可继续相关只读调研。用户已给足够参考、同一机制已核实且源码未变时直接复用；简单改动以已读当前实现为依据，不为形式重复搜索。编辑已有扩展先 `noname_read_extension` 读当前代码。
4. **源码核验与检索**：noname_search_reference 用于查找相似技能、武将和卡牌实现；引擎 API 用通用只读工具查当前游戏源码，包括相关 .js/.ts、类型与必要文档，按实际项目结构定位。
   - **核对实际用法**：对 API 参数或行为有疑问，或准备判为不支持、参数无效时，先读当前定义、参数处理和直接相关分支，给出依据位置。使用参考前读相应实现，不把翻译、注释或相邻条目当作该技能。搜索未命中不等于不支持，不据此删除参数或功能。
   - **完成当前任务**：参考和证据足够后继续完成当前武将、卡牌或模式；可组合不同机制的参考，复用源码未变的已核实结论，不要求穷举候选或审计整个引擎。证据不足、读取失败或存在冲突时，说明具体未决问题与限制，不猜测。遵守宿主权限、预算、超时与取消。
   - **范围与写入**：从已配置的游戏路径定位所需源码，按需读取，避免重复或无关检索；不在盘符根、整个用户目录或 DSH 安装目录盲目寻找游戏。游戏源码保持只读，扩展修改仍经 noname_write_extension 校验及原有写入门禁。本机源码查证、扩展读写需要有效游戏目录；未配置时请用户提供或在工坊设置中配置。已有参考足够的只读讨论或仅生成可以继续，缺少目标引擎证据时说明具体兼容限制。卡牌参考检索用 type:'card'。
读取与发现采用明确分页：仅按当前问题需要续读目录/工具/技能列表或源码，分别使用 offset/limit 与字符 offset/limit，并复用 coverage.snapshot 作为 snapshot；源码变化时重新查询，不混合页面。coverage 未完成、资源上限、解析失败、歧义都不能解释为条目不存在。搜索 5 GiB 上限只适用于分块检索；静态解析有独立上限。手动写入较长成品返回 draftId，用 noname_read_extension 在同一会话中分页读取，直到 pagination.complete=true；草稿闲置15分钟过期，不写入游戏文件。

5. **确定范围并精确修改**：先读目标条目和已勾选技能，必要时用 `listBlocks` 定位文件，再按 `file` 与 `block` 读取。允许修改本次目标、用户指定的新增内容，以及实现需求必需的直接关联翻译、辅助技能、注册或播放挂载。关联修改前核对实际调用关系、所属文件及影响面，简述必要性；不能仅凭“相关”扩大到其他武将、无关功能或整包重构。共享代码确有必要调整时保留其他调用者行为；需要改变无关玩法时先澄清范围。优先用 `blocks` 提交完整目标区块，用唯一命中的 `edits` 修改零星或非条目位置；删除用 `deletes` 明确声明且须属于用户需求。未提交区块由工具保留，仍核对实际差异与返回结果。新包首写按骨架给条目加锚点；全文模式仅用于首写或未建索引的存量包兜底。多文件包每次 read/write/validate 都传实际归属的 `file`，缺省仅代表 extension.js；不得把目标条目的文件沿用到其他文件的辅助技能或挂载。
   **存量全文限制**:自动或手动任务都必须显式给 `editScope`;仅允许唯一的既有 ID(可用 `kind:id` 限定)。imports/precontent/骨架/注释/CRLF/尾空白等未授权原文完全保留,不做行尾归一。新增/删除用区块,其他区域用唯一原文 `edits`(未建索引也支持)。正则、除法、模板插值或区间歧义导致全文拒写时,改用精确补丁,不要扩大授权重写文件。
6. **按实际文件校验**：`noname_validate` 的 `file` 与读写目标一致，缺省为 extension.js。入口检查语法及扩展结构，其他 .js 文件按 ES Module 语法检查，.json 检查 JSON 格式；子模块不要求入口的 name 字段。校验与写入工具共用文件分类，写入仍只支持扩展 .js 源码，info.json 由入口写入的 infoJson 参数处理。独立预检时传完整文件内容，不把每个技能片段都当完整入口校验。blocks/edits 可直接交写入工具组装并按同一规则检查，无需为预检重抄整文件；手动方式也会检查完整成品。error 修复后重验，warning 结合当前源码与需求判断；格式或语法通过不代表玩法、联机或界面已经实测。
7. **落盘前自查**:写入前对照本次需求与已确定的方案自查(触发/频率/目标/数值/边界/不做什么,逐条能在代码里指出来),发现偏差先改再写。
8. **写入**:自查通过后 `noname_write_extension`(或手动模式由用户复制)。
9. **收口**:核对本轮实际写入或手动成品交付成功后调用 `noname_skills_written` 原样带回任务ID,`skills` 只填本轮实际改动的任务技能名称,提示用户进游戏测试;实测出引擎级可复用结论(API 行为/全局坑)时用 notes 参数一并提交,禁止写本任务实现细节。
10. **问题反馈**:先读当前代码，依据证据定位原因并修复；写入失败或成品未交付时，不把任务节点登记为完成。

## 存量包与部分索引
读取返回的 file、coverage、歧义与跳过项后再选择修改目标。建立索引会备份并添加定位注释，必要时也可能补条目末尾逗号；部分索引仅覆盖能安全定位的定义。同名、非连续或不可定位内容保持原样，不能当作不存在，也不能猜选来源。未索引或非条目区域可用唯一原文 edits；不要删改定义、改名、扩大 editScope 或整包重写来让索引强行通过。

## 图片/素材约定
- 图片(立绘/卡面图)统一**平铺**放扩展文件夹的 image/ 子目录,文件名 = `<内部ID>.jpg`(用 noname_copy_images 复制;其目标只能是纯文件名,不支持子目录);不要散放根目录。
- **引擎默认立绘路径是扩展根目录**(extension/<包名>/<武将ID>.jpg),不会自动找 image/ 子目录——图片复制进 image/ 后,武将条目必须显式写 `img: "extension/<包名>/image/<武将ID>.jpg"`;卡面图在卡牌定义里同理显式写 `image: "extension/<包名>/image/<卡牌ID>.jpg"`(配 fullimage: true),否则游戏里显示默认图。
- 没有图片时,交付说明必须提醒用户补图(mode 任务交付的是玩法不是立绘,无图是常态,不需提醒)。

## 武将的可选需求
- 任务带「新势力」时，名称是势力显示名，图片是势力标识图；把新武将归入该势力。先核对当前引擎及启用 UI 的注册、翻译与图片用法，内部 ID 遵守任务前缀并避开重名，不覆盖已有势力。注册代码和素材留在本扩展内。
- 参考做法：先核对现有扩展的有效实现；原生注册适用时，在合适的初始化阶段（常见为 precontent）使用 game.addGroup(内部ID,显示简称,完整名称,配置对象)。配置对象中的 image 引用已复制的扩展内势力图，color 按显示需要设置；武将的 group（旧数组格式的第二项）使用同一个内部 ID。核对 lib.group、名称翻译及 lib.card["group_"+内部ID] 的图片是否生效。当前已读引擎中，普通新势力使用默认注册类型，不要为了显示在选项里就加入 lib.selectGroup；该列表可能让武将开局重新选择势力，具体语义以目标环境为准。先沿现有扩展和实际启用环境，核对势力注册、候选生成、确认结果和最终武将归属。game.addGroup 存在不代表旧扩展、模式或 UI 已接入；保留已有有效兼容方案，不仅因存在原生接口就删除或替换。链路有缺口时，可以使用必要的全局注册、全局技能或界面钩子，结合用户反馈和实际实现限定改动范围。核对本地玩家、AI 与联机结果，以及重复触发和监听生命周期；不要把单机 game.me 的处理直接套给所有玩家。额外玩法只按用户需求实现。注册、图片与选择势力的区别见[自建势力参考](references/custom-faction.md)，路径以本技能资源目录为基准，按需读取。
- 势力图片使用 noname_copy_images 单独复制到 image/，使用独立文件名并保留真实后缀；不带 taskId，也不与武将立绘合批登记。taskId 会把首张图片记为武将立绘，势力图不能充当立绘交付。
- 任务带「视频动态立绘」时，使用 noname_copy_videos 复制视频，并按当前引擎和启用 UI 实现立绘挂载与静音循环播放、缩放、点击透传和退出清理。不能只把 MP4 路径写入静态 img 字段，也不能把复制成功说成播放已验证。
- 参考做法：保留静态底图，在实际头像节点内叠加 video（常见为 player.node.avatar；副将需核对 avatar2 并独立绑定），用 lib.assetURL 拼接扩展内相对路径，设置 muted/loop/autoplay/playsInline、object-fit:cover 和 pointer-events:none，先透明，确认播放后再显示；失败则撤掉视频露出底图。按武将 ID、头像槽位和路径比对，换将、禁用或离场时暂停、释放视频并清理监听与定时器；不要照搬无期限轮询或永久失败缓存。头像循环不调用全屏技能视频的暂停/恢复逻辑。具体流程与适配边界见[视频立绘参考](references/video-portrait.md)，路径以本技能资源目录为基准，按需读取。
- 编辑已有武将也可使用视频动态立绘；只修改任务指定的武将，沿用已有静态立绘和无关技能。先读已有播放逻辑，必要挂载先定位实际归属文件，每次写入带对应 file，再用唯一原文 edits 精确修改，不重建武将或整包重写。本次没填新图片路径不等于缺图，先核对原有静态立绘。视频单独修改也会登记对应任务节点，完成后按消息给出的节点名称回报。取消勾选表示本次不提出视频修改，不表示删除旧视频或关闭已有动效。
- 静态立绘独立保留，已提供时用作视频加载或播放失败的回退；没有静态图时说明缺图，不把视频或势力图登记为静态立绘图片。任务的 newFaction / portraitVideo 保存的是需求，不是素材已交付的凭证，原有图片与配音完成条件不变。
- 需求理解和交付检查覆盖已勾选的选项；没有这些区块时不自行添加新势力或视频立绘。手动模式仍只生成源码成品，素材按用户已授权范围处理，全部手动时提供资源清单。

## 配音约定(音频只放扩展包内,绝不放游戏本体 audio/ 目录)
- **技能配音**:新增自带技能配音时，技能对象写 `audio: "ext:<包名>/audio/skill:<句数>"`(两句就是 :2,一个技能任意多句),文件放 extension/<包名>/audio/skill/<技能内部ID>1.mp3、<ID>2.mp3……(mp3,内部ID+从 1 连号,句数与 audio 数字一致)。复用已有配音时，先核对当前引擎支持的引用方式及目标资源；已有音频引用不一概要求带 ext:。audio: 2 / audio: true 等写法会触发校验 warning，应核实资源来源；新增音频仍只放扩展包内，不向游戏本体 audio/ 写入。
- **阵亡语音**：优先沿用当前引擎的默认命名与扩展包 audio/die/ 路径；支持默认查找时无需附加实现代码。已有数组/对象武将定义、显式音频引用或 dieAudios 等字段按当前实现核对，不把某一种示例写法推广到所有版本。
- 复制配音用 `noname_copy_audio`:target 必须是 `skill/<内部ID><序号>.mp3` 或 `die/<武将ID><序号>.mp3`;技能配音条目带 `skill` 参数(任务里的技能显示名),交付才计入任务收口。任务消息带「配音/阵亡语音」区块时按列出的句数与路径逐条复制。

## 视频复制约定
- 用户提供本地视频绝对路径后，直接用 `noname_copy_videos` 复制到 `extension/<folder>/video/`，不要求用户手动搬文件。参数为 `folder`、`videos:[{source:绝对路径,target:纯文件名}]`，可选顶层 `overwrite` 默认 `false`。
- 支持 mp4、webm、m4v、mov、ogv；target 只填中文/字母/数字/下划线/连字符组成的文件名加原视频后缀，总长不超过 200，不含子目录。源路径可带空格，无需先重命名源文件。
- 已有同名目标时默认不覆盖；需要覆盖时显式传 `overwrite:true`，工具先备份到扩展包 `backup/video/` 下，再原子替换目标。
- 按返回的 `copied`（如 `video/开场.mp4`）、`backups:[{target,path}]` 和 `errors:[{source,target,error}]` 逐项核对并说明结果；部分成功须列出成功与失败项。视频复制不登记任务，也不改变任务完成条件。
- backups.path 是相对扩展包的路径；恢复时用当前游戏目录/extension/<folder>/拼成绝对 source，target 用原视频文件名，明确覆盖时传 overwrite:true，恢复也会先保留当前视频。
- 工具只复制文件、不转码；文件复制成功不代表当前引擎或视频编码一定支持播放，播放需求须结合当前引擎源码与实际游戏验证。

- 素材工具可用性以当前安装的实际工具列表为准；缺少工具或复制失败时据返回值说明具体原因，不伪装成图片改后缀、不输出假调用、不修改安全设置绕过写入。新建视频目前需要文件系统支持硬链接，遇不支持的磁盘时明确兼容限制，不能将其说成视频损坏。
- 手动模式控制源码成品是否写入，不等于素材与任务登记不落盘；素材复制按用户已授权的范围执行。用户要求全部手动时交付代码与资源清单，保持该范围。

## 技能字段示意(filter / cost / content 按技能类型选用)
```js
{
  audio: "ext:包名/audio/skill:2",  // 自带配音示例:两句,文件 audio/skill/<内部ID>1.mp3、<ID>2.mp3；复用已有配音先核实引用方式
  enable: "phaseUse",        // 主动技;或 trigger: { player: "phaseBegin" }
  usable: 1,
  forced: false, locked: false, frequent: false,
  filter: function (event, player) { return true },
  filterTarget: function (card, player, target) { return target != player },
  selectTarget: 1,
  cost: function (event, trigger, player) { /* 可选段:发动代价/前置选择;其 event.result.bool 为 true 才执行 content */ },
  content: function (event, trigger, player) { /* 新式用 async 并 await 每步 */ },
  ai: { order: 6, result: { target: function (p, t) { /* 0 为占位，成品按实际效果对目标的收益/损害评分 */ return 0 } }, expose: 0.2 },
}
```
字段示意中的 0 分和空效果都是占位，交付时按实际玩法补齐，不视为已实现的技能。
- 主动技(enable)必须写 ai 字段,否则 AI 不会用。
- ai.result.target 按动作对目标的收益/损害和实际评分流程填写，并核对态度权重；正负分不是简单的敌友标签。
- 采用 async content 时按当前引擎约定等待相关事件完成；步进写法保持对应事件流，不混用不兼容的 await 或结果变量。
- 改 lib/_status 全局状态要考虑联机(game.broadcastAll)。

## 联机兼容与界面同步
先按当前引擎确定主机、操作者、其他客机各自加载和执行哪些内容，再分开处理权威结算、选择回传、状态同步与本地显示。

- 核对扩展包启用方式、技能加载条件以及 connect / forceLoad 等选项的真实作用；设置一个字段不等于技能和界面已完成联机适配。
- 随机结果由实际负责结算的一方确定，再传递可复用的结果；核对广播是否同时在发送端执行，防止各端独立随机或本地加广播造成重复结算。
- 广播/远端回调使用当前消息机制支持的参数，不依赖主机闭包、局部函数或 DOM 节点。显示窗口与游戏状态分别同步；主机出现了界面不能作为客机可见、可操作的证据。
- 选择流程处理无合法选项、取消、回传、等待及连接丢失；根据需求保护隐藏信息。派生卡的依赖和本局牌堆单独核对，不假定单机配置自动带入联机。
- 本轮涉及联机或自定义 UI 时，按需求检查主客各端能显示和继续操作、效果只结算一次；没测客机就说明该项未验证。详细排错按需查看本技能的制作与排错指南。

## 常见问题(静态检查与游戏验证)
校验返回 error 时必须修复并重验，写入工具会拒写；warning 是需结合当前源码和需求判断的提示。触发、效果、AI 与联机等语义仍需游戏内验证，静态检查通过不代表没有 bug。
1. 代码区全角标点/引号(字符串内中文标点没事)
2. name 与文件夹名不一致(新式直接不加载)
3. 面向玩家展示的条目缺少所需的名称或描述 translate
4. async 内容未等待所需事件、步进/async 混用、主动技 AI 缺失或收益/损害评分方向错误
5. 新旧写法混用

## 诊断与反馈循环
- content 关键步骤插临时 `game.log(...)` 供用户游戏内查看;稳定后移除。
- 用户反馈问题:先 `noname_read_extension` 读当前真实代码,再定位修复;不要凭对话记忆改。
- 每轮反馈自动累加轮次;完成后 `noname_skills_written` 原样带回任务ID,`skills` 只填本轮实际修复的技能,不得回传整组未改技能。已确认技能默认保留;如果本轮确实修改了某个已确认技能且需要重新测试,将其名称同时列入 `skills` 与 `retestSkills`,未修改的技能不得列入 `retestSkills`。

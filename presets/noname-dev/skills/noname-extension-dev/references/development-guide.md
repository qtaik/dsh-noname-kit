# 武将、卡牌与模式的制作和排错指南

围绕用户本次已确认的玩法选择相关部分；已有足够依据时继续完成实现。这里的检查项用于发现遗漏，无需每次逐项向用户汇报或运行整张测试表。扩展读写、任务登记和素材复制仍按主技能文档及实际工具参数执行。

## 怎样使用教程和当前源码

1. 以工坊当前显示的游戏目录、目标扩展和任务消息为起点，先识别引擎版本、入口文件及已有写法。保留用户已有包的结构；新版文档中的写法不自动适用于旧版引擎。
2. 用户提供本地教程目录时，可用通用只读工具查看其 `README.md`、目录文件和相关章节。`noname_search_reference` 搜索配置游戏目录内的参考实现，`noname_list_catalog` / `noname_read_catalog` 读取游戏内容源码；这些工具没有自动索引外部 Markdown 教程。
3. 教程用于理解概念、定位关键词和案例。API 签名、调用时序、参数含义与联机行为有疑问时，读当前游戏源码的定义及直接相关调用；类型声明辅助理解。实际实现与教程冲突时说明版本或用法差异，按当前目标环境实现。
4. 查到一个可用思路不代表其中每个辅助方法都由引擎提供。先区分内置 API、案例自定义函数、伪代码与省略片段，补齐实际依赖后再使用。
5. 章节或文件缺失时，明确当前资料缺口，继续利用已有资料和当前源码；不补造内容、不为读完教程而暂停已有依据的开发。新的玩法歧义才需向用户澄清。

常见教程的章节名称可用于定位，不要求教程必须采用这些文件名：

| 本次问题 | 可按需查看的章节 | 当前环境还需核对的内容 |
|---|---|---|
| 扩展加载、多文件入口、注册 | `structure.md`、`basic.md` | 实际加载器、导出格式、注册时机和路径 |
| 武将数据与显示 | `character.md` | 数组/对象格式、技能关联、翻译及图片字段 |
| 触发、选择、技能效果 | `skill.md`、`trigger.md`、`condition.md`、`effect.md` | 事件结构、取消结果、效果顺序和次数限制 |
| 标记、储存、临时技能 | `mark.md`、`skill-types.md` | 初始化、同步、过期与移除清理 |
| 卡牌和牌堆 | `card.md` | 目标选择、结算、装备/延时牌与实体牌堆 |
| 电脑决策 | `ai.md` | 评分调用、态度、可选动作和代价 |
| 联机界面与状态 | `online.md` | 主客执行位置、消息参数和重复结算风险 |
| 配音和资源 | `audio.md`、API 附录 | 当前音频字段、实际路径与插件素材工具约定 |

例如 Antarctics 的《无名杀扩展开发教程》可以作为学习资料，但不能代替当前引擎实现。教程未标明兼容版本、示例只经过浅测、依赖自定义组件，或目录列出了不存在的章节时，分别记录实际范围。不要把充能条案例中的自定义函数直接当作引擎 API，也不要把案例的素材目录覆盖到本插件的资源约定。

## 从玩法到技能实现

- **触发与事件链**：明确谁触发、何时检查、每个目标还是整个事件执行一次，以及父事件是否影响条件。依赖历史记录或父事件时，核对事件层级和已完成状态，避免把上一张牌或其他角色的事件当作本次来源。
- **字段按技能类型选用**：主动、触发、视为、规则修改和纯标记技能需要的字段不同。`filter`、`cost`、`content` 不是每个技能都必须照填的三段；`forced`、`locked`、`direct`、`charlotte` 等字段的行为分别核实，不能仅凭中文“锁定技”互相替换。
- **条件与代价**：查询条件尽量保持无持久副作用；不要在可能反复调用的 `filter` / `mod` 中扣牌、记发动次数或留下过期缓存。代价是否真实支付、取消后是否发动、失败后是否计次，按需求和当前事件机制处理。
- **选择与取消**：分别处理无合法目标、用户取消、选择成功、目标中途失效。实际读取当前选择 API 的返回值；异步流程使用当前事件及明确变量，不混用示例中的隐式 `result`、`target`、`targets`。
- **效果顺序**：按玩法顺序处理摸牌、弃置、伤害、失去体力、回复、获得牌等，区分这些事件的实际语义。涉及异步事件时按当前编译器支持的方式等待完成；沿用步进写法时不混入不兼容的 `await` 或闭包依赖。
- **次数与重置**：明确“每回合”“每阶段”“每轮”“每名角色”各自的归属和重置时间，取消与无效发动是否消耗次数，别用一个永久布尔值替代所有限制。
- **标记与储存**：定义初始化、读写者、显示与移除清理；按本次机制处理死亡、换将、技能丢失、临时效果到期和下一局。储存牌、玩家或事件对象时确认序列化与生命周期，避免长期保留失效引用。
- **视为与规则修改**：核对可用牌/可选目标、响应场景、距离与次数修正、子卡移动及派生技能注册。规则查询返回值以实际调用处为准，避免把某个距离技巧变成所有场景的固定返回值。
- **AI**：按动作对目标的收益/损害与实际评分流程填写结果，再核对态度权重、代价、时机及无人类交互时的选择。不要把 `ai.result.target` 的正负直接当作敌友标签；避免在评分函数里修改游戏状态。

## 卡牌和模式

卡牌先确定是实体牌堆牌、技能创建的牌、派生牌还是视为牌。名称、类型、花色点数、目标范围、使用与响应、结算顺序、翻译和卡图按实际交付需要补齐；只有设计上需要进入实体牌堆的牌才安排对应牌堆条目。牌堆元组、属性/nature 等可选信息及 `selectTarget` 的特殊值，以当前引擎读法为准。

装备还要考虑装备栏限制、替换、获得与失去装备时的技能生命周期；延时牌还要考虑判定、转移、无效与离场。不要只写一个 `content` 就声称装备或延时机制完整。

模式按已确认的人数、角色/阵营、先手、回合结构和胜负条件设计完整闭环。按当前引擎与相近模式核对注册入口、设置读取、选将、玩家 ID、座次、AI 态度、牌堆、开始与结算时机。`game.addMode`、模式事件与 UI 的具体写法需要匹配目标版本；旧项目的临时修复和历史经验不作为跨版本保证。

## 联机与自定义界面

- 先分清权威结算、玩家选择、每台机器的显示，以及旁观者可见内容。决定随机结果的一方应传递可复用结果，避免各端各自随机导致分歧；同一个效果也不能因本地执行加广播而重复结算。
- 核对当前引擎的包启用、技能加载和执行规则，再使用 `connect` / `forceLoad` 等选项。给技能加一个字段不能自动完成联机适配；派生卡的依赖方及本局牌堆也要单独确认。
- 广播回调中的变量应能通过当前消息机制传递或在接收端定位。不要依赖主机闭包、局部函数或 DOM 节点。`broadcast` / `broadcastAll` 是否在发送端也执行、怎样解析玩家与卡牌参数，以当前源码为准。
- 状态同步和界面显示分别处理。主机创建了窗口不代表客机会得到同样的窗口；选择还需处理控制者、回传、等待、取消、超时及连接丢失，避免客机无限等待。
- 界面优先复用引擎节点和对话框。玩法确需定制界面时，考虑缩放、层级、关闭和清理，配合用户实际 UI 扩展验证；不通过“一律禁止定制界面”回避玩法需求。

## 素材与实际交付

自建势力可参考[注册与势力图实现](custom-faction.md)：统一内部 ID、显示名、势力图及武将归属，并区分固定势力和开局选择势力。

视频动态立绘可参考[头像层视频实现](video-portrait.md)：保留静态底图、在头像内叠加视频，并处理换将、失败回退和资源清理。

源码改动走 `noname_write_extension`；素材走各自的复制工具。图片复制后核对条目的 `img` / `image` 引用，配音复制后核对实际文件名与音频字段，视频复制后另行验证编码支持、挂载与播放。复制成功、任务登记成功和游戏内呈现成功是不同结果，分别据返回值和实际观察说明。

编辑存量包时先读实际内容与文件归属。部分索引留下的同名或不可定位定义要保留；对未索引区域可用唯一原文 `edits`，不要通过删除同名定义、猜选来源或整包重写来绕开歧义。手动源码模式也要分清草稿生成与素材复制、任务登记等独立落盘操作；用户要求全部手动时按该范围交付。

## 选择相关验证项

| 机制 | 常见的最小检查 |
|---|---|
| 触发与次数 | 应触发/不应触发、连续事件、次数耗尽与重置 |
| 选择与代价 | 确认、取消、无目标、资源不足、目标中途失效 |
| 储存与临时效果 | 到期、移除、死亡/换将以及再次进入对局 |
| 卡牌 | 合法/非法目标、使用/响应、牌堆来源、装备或延时生命周期 |
| AI | 不会卡在必须有人类点击的选择，收益与代价方向合理 |
| 联机/定制 UI | 主机和客机各自可见并能操作，效果仅结算一次，取消后双方都继续 |

按改动选择需要的检查即可。静态语法/规则校验通过，只能说明该范围的检查通过；没运行游戏、没连接客机、没测试新版本的内容都不改称已通过。交付说明写清本轮实际修改、验证结果和具体剩余问题，不重复索要已确认需求，也不为无关项目扩展测试范围。
